The Software Engineering Loop

Development as decision-making under an unknown specification

Abstract

In program synthesis the specification is given. In software engineering it is not: the people who will judge the software cannot state in advance what they want, and what they want changes in response to what is built. We model development as a partially observable decision process whose hidden state is the stakeholder’s current specification and whose actions are programs. A rejected program then reflects one of two failures: a program that does not satisfy its specification, or a specification that does not describe what is wanted. From the model we derive a procedure a person or an agent can operate, the software engineering loop: keep a single working specification as a finite set of logical sentences, classify each piece of new information by the failure it reveals, revise the specification, and reconcile tests and code with it.

1. Introduction

Brooks (1987) argued that the hardest part of building software is deciding precisely what to build. Requirements are incomplete, specification and implementation are intertwined (Swartout and Balzer 1982), and software in use must keep changing (Lehman 1980). The field has many process models and techniques that respond to these observations. This article offers a compact model of the problem they address and derives a working procedure from it. We take the central problem to be this:

Software engineering is the problem of producing programs when the specification they must satisfy is unknown, must be inferred from interaction with the people who will judge the programs, and may change as a result of that interaction.

On this view, producing a program for a given specification, the problem studied by program synthesis, is one component of a solution. The others are forming a belief about the specification, revising it as new information arrives, and choosing programs under it. A developer must therefore get two things right, and they can fail independently. When a delivered program is rejected, either the program does not satisfy the developer’s specification, a failure of correctness, or that specification does not describe what was wanted, a failure of adequacy. The first calls for changing the program and the second for changing the specification.

We state the model at three levels, each an approximation of the one before. The first is the problem: a partially observable decision process whose hidden state, the specification currently wanted, moves in response to what is built (Section 3). Its ideal solution is intractable, but it fixes what counts as success and what any practical method approximates. The second is an approximation in which the developer maintains a single working specification, written as a finite set of logical sentences (Sections 3.3 to 5). The logic is there to make the decision process concrete: it yields objects that can be written down, checked and revised. The third is practice, in which people and agents make the judgments that the approximation calls for heuristically and in natural language. The developer enters the model only through the programs it produces, so the model does not distinguish human from AI developers.

2. The problem

2.1 Objectives and specifications

Let $\mathcal{P}$ be the set of programs.

Definition 2.1 (Objective). At time $t$ the stakeholder has an acceptance set $A_t \subseteq \mathcal{P}$: the programs it would accept. This set is the objective at time $t$. The stakeholder judges behavior, so two programs that behave identically are either both acceptable or both not.

The engineering problem at time $t$ is to produce some $p \in A_t$.

Definition 2.2 (Specification). A specification $S$ is a finite description that a program $p$ either satisfies, written $p \models S$, or does not. Its set of models is $$\operatorname{Mod}(S) = \{\, p \in \mathcal{P} : p \models S \,\}.$$

Definition 2.3 (Latent specification). We assume that at each time $t$ the objective admits a description of practical length: a specification $S^*_t$ with $\operatorname{Mod}(S^*_t) = A_t$ that states a condition on behavior rather than listing programs. Several specifications may describe the same objective; nothing below depends on the choice, and we call any one of them the latent specification.

The latent specification is not known in advance, either to the stakeholder or to the developer: the stakeholder can judge a program it is shown but cannot state $S^*_t$. If it were known, the engineering problem would reduce to program synthesis: producing a program that satisfies a given specification. Software engineering, in short, is synthesis under an unknown specification.

Two idealizations should be noted. The single stakeholder stands for what may be several people with conflicting wishes; the model treats them as one source of judgments, and the loop of Section 5 reports the conflicts it detects rather than resolving them. And because the stakeholder judges behavior, the objective covers only what can be observed of the software. Qualities of the program text, such as how easily it can be changed, enter the model only through the cost of modification (Section 3.1).

2.2 Capability and belief

Fix a time $t$. We model the developer as an agent, human or AI, that holds a belief about the latent specification and produces a program for the specification it believes is wanted.

Definition 2.4 (Capability and belief). The developer’s belief $b$ is a probability distribution over specifications. Its capability $\pi(p \mid S)$ is the probability that it produces program $p$ when working from specification $S$. The program it delivers has distribution $$\pi(p) = \sum_{S} \pi(p \mid S)\, b(S).$$

A delivered program is accepted when the developer believes something close enough to what is wanted and then builds what it believes. Acceptance needs both factors: a developer of perfect capability is accepted only as often as its belief leads it to acceptable programs. Program synthesis studies the first factor with the second held certain.

2.3 Adequacy and correctness

Definition 2.5 (Adequacy and correctness). A specification $S$ is adequate at time $t$ if $\operatorname{Mod}(S) = A_t$. A program $p$ is correct with respect to $S$ if $p \models S$.

Correctness relates the program to the specification and is governed by capability. Adequacy relates the specification to the objective and is governed by belief.

The two are linked by a simple observation. If $p$ is correct with respect to $S$ and every program that satisfies $S$ is acceptable, then $p$ is acceptable. So when a program is rejected, either it is not correct with respect to $S$, or $S$ admits an unacceptable program and is not adequate. A rejection is evidence against one of two conjectures, and a developer that does not distinguish them cannot know whether to change its program or its specification.

Adequacy is defined by equality rather than inclusion because a specification can also be too strong: if $\operatorname{Mod}(S) \subseteq A_t$ and $\operatorname{Mod}(S) \ne A_t$, every correct program is accepted, but the specification excludes acceptable programs and so constrains the developer needlessly. No rejection reveals this kind of inadequacy, a limitation we return to in Section 6.

Example 2.6 (Withdrawal). A bank asks for a withdrawal operation. Its input is a triple $x = (b, k, m)$ of a balance $b$, an account kind $k \in \{\mathrm{standard}, \mathrm{premium}\}$ and an amount $m$; balances and amounts are in cents and bounded by the range of machine integers, and a balance is negative when an account is overdrawn. The developer specifies that a withdrawal of a positive amount not exceeding the balance succeeds and reduces the balance by that amount, and that every other withdrawal is rejected and leaves the balance unchanged. It then delivers a program.

Two things can go wrong. First, the bank may want premium accounts to be able to overdraw by up to $100. The specification is then inadequate, and no amount of work on the program will satisfy the bank unless the specification changes. Second, the program may permit a withdrawal that the specification forbids. The program is then incorrect, and the specification needs no change. In both cases the bank reports the same kind of event: a withdrawal that succeeded or failed when it should not have. Telling the two apart is the developer’s job. We return to this example in Section 5.3.

3. Development as a decision process

3.1 The process

Development proceeds in steps: the developer delivers a program and the stakeholder responds.

Definition 3.1 (New information). On receiving $p_t$, the stakeholder returns new information $\delta_t$: a requirement it states, a judgment of $p_t$, or a report of the behavior of $p_t$. The initial program $p_0$ may be empty, in which case $\delta_0$ is the stakeholder’s first request.

Definition 3.2 (Decision process). At each step $t$:

  • the state is the pair $(S^*_t, p_t)$ of the latent specification and the current program, of which $S^*_t$ is hidden from the developer;
  • the observation is the new information $\delta_t$, which depends on the state;
  • the action is the next program $p_{t+1}$;
  • the latent specification then moves to $S^*_{t+1}$, and the move may depend on the program just delivered;
  • the reward is acceptance of the new program, less the cost of modifying the current program into it.

Since $S^*_t$ is hidden, this is a partially observable Markov decision process (Kaelbling et al. 1998), and the developer is its agent. The model needs only that reward rises with acceptance and falls with the effort of changing the program; the cost term is why developers modify existing systems rather than rebuild them.

The moving objective is what separates this process from learning a fixed target. Because the next specification may depend on the program delivered, delivering a program both reveals information about the objective and may change it, as when stakeholders discover what they want by seeing what has been built. The model does not assume a fixed objective waiting to be discovered, only a current one at each step. New information may therefore reflect a change in the objective or an error in the developer’s belief about it.

3.2 The ideal solution

A solution to the decision process has two parts:

  • a belief update, which maps the current belief, the program delivered and the new information to the next belief, $(b_t, p_t, \delta_t) \mapsto b_{t+1}$;
  • a policy, which maps the next belief and the current program to the next program, $(b_{t+1}, p_t) \mapsto p_{t+1}$.

Ideally the belief update is Bayesian: each candidate specification is reweighed by how well it explains the new information and by how specifications tend to move once a program is delivered. Such an update weighs change and error together, so the developer need not determine which occurred. The belief and the current program then summarize the history: the best action depends on past programs and information only through them.

When $S^*_t$ is known and fixed, the belief is a point mass and the policy reduces to the capability $\pi(p \mid S^*_t)$ of Definition 2.4. The rest of a solution arises only when the specification is unknown: forming a belief from the first request, updating it, and choosing programs partly for the information they will elicit.

The ideal solution is out of reach. A belief over all specifications cannot be written down, the history that determines it grows without bound, and computing an optimal policy is intractable even for finite processes of this kind (Papadimitriou and Tsitsiklis 1987). Its use is as a reference: it says what a practical method approximates and what that method gives up.

3.3 A working specification

The approximation we consider replaces the belief with a single specification.

Definition 3.3 (Working specification). The developer maintains a single specification $\hat{S}_t$, its working specification. At each step it revises the working specification in light of the new information, then produces the next program from the revised specification and the current program: $$\hat{S}_{t+1} = U(\hat{S}_t,\, p_t,\, \delta_t), \qquad p_{t+1} \sim \pi(\,\cdot \mid \hat{S}_{t+1},\, p_t).$$

The developer acts as if its working specification were the latent one. The revision $U$ takes the place of the belief update, and capability, now conditioned on the current program as well, takes the place of the policy: it is the means by which new information changes what the developer acts on. Three objects must be kept apart (Table 1).

Table 1. The three specification-related objects of the model.
ObjectMeaningHeld by
$S^*_t$ latent specification: what is currently wanted implicit in the stakeholder’s judgments
$b_t$ belief about $S^*_t$, in the ideal solution an ideal developer
$\hat{S}_t$ working specification, in place of $b_t$ the developer, explicitly

The working specification summarizes the history in a form whose size depends on the objective rather than on the length of the history. This matters when a language model serves as the policy, because its context is bounded: it can be given $\hat{S}_{t+1}$ and $p_t$ in place of the history.

The current program cannot serve as this summary. It is an action: the policy produces it, and it reflects the developer’s training and the cost of modification as well as the specification. The stakeholder does not distinguish programs that behave identically (Definition 2.1), so most of what distinguishes one program from another, including its language and structure, corresponds to nothing in $S^*_t$. It enters the policy only through the modification cost and can be omitted where that cost is negligible.

The working specification is also what makes the observation of Section 2.3 usable. With $S = \hat{S}_t$, a rejected program that is correct with respect to the working specification shows that the working specification is inadequate, while a program that is not correct has a defect whether or not the specification is adequate. Without an explicit working specification there is nothing to check correctness against, and the two failures cannot be separated.

The approximation has costs. A single specification does not record how uncertain the developer is, so a policy acting on it does not choose programs for the information they would yield. The revision $U$ also has less to work with than a full belief update, since whatever is discarded in forming $\hat{S}_t$ is lost. Keeping several candidate specifications, or recording the points on which $\hat{S}_t$ is unsettled, would give closer approximations.

4. The specification as a theory

This section gives the working specification a form that can be written down and operated on: a theory, a satisfiable set of sentences about how the software should behave. We write $S_t$ for $\hat{S}_t$.

4.1 Sentences

Definition 4.1 (Sentence). A sentence is a statement about the software’s behavior of the form $\forall x \in D.\ P(x)$, where the finite set $D$ is its domain.

A requirement with an existential quantifier is brought to this form by fixing a witness: “within 5 seconds” instead of “eventually.”

Definition 4.2 (Satisfaction). A program satisfies $\forall x \in D.\ P(x)$ when, for every $a \in D$, its behavior has the property $P(a)$. The restriction of the sentence to $\{a\}$ is its instance at $a$. A program satisfies a set of sentences if it satisfies each of them. A set is satisfiable if some program satisfies it, and it entails a sentence if every program that satisfies the set also satisfies the sentence.

From here on, a specification is a finite, satisfiable set of sentences.

4.2 New information

Checking adequacy is validation (Boehm 1984); checking correctness is verification. Tests check sentences only at sampled elements, so they can reveal failures but never establish their absence (Dijkstra 1970). Type-checking establishes the sentences expressed by types over their whole domains.

New information takes one of three forms. A stated requirement is a sentence. A judgment of the program is a counterexample. A withdrawn requirement is a retraction, which names a sentence $h$ in $S$ and the part $X$ of its domain on which $h$ should no longer hold.

Definition 4.3 (Counterexample). A counterexample is an observed case in which the program’s behavior differs from what was expected, given by a condition, an expected value and an observed value. Its instance is the sentence that the expected value is produced under the condition.

Definition 4.4 (Entailment check). The entailment check determines which conjecture new information refutes.

  • A sentence $g$ refutes adequacy if $S$ does not entail $g$, and refutes neither conjecture otherwise.
  • A counterexample refutes correctness if $S$ entails its instance, and refutes adequacy otherwise.
  • A retraction always refutes adequacy.

If the working specification entails the expected behavior, the program failed to meet its specification; otherwise, the specification failed to describe what was expected.

A counterexample that refutes adequacy comes with a generalization stated by whoever reported it: a sentence that entails its instance.

4.3 Revision

Definition 4.5 (Restriction). A restriction of $\forall x \in D.\ P(x)$ is $\forall x \in D'.\ P(x)$ with $D' \subseteq D$. Restriction to the empty domain removes the sentence.

Definition 4.6 (Revision). Let $g$ be a satisfiable sentence. A revision of $S$ by $g$ is a satisfiable specification obtained by adding $g$ to $S$ and restricting as few sentences of $S$ as possible, each as little as possible.

Existing sentences are never rewritten, only restricted. When $S \cup \{g\}$ is satisfiable, nothing is restricted. Otherwise there may be several revisions, and choosing among them is a judgment about which existing requirements the new one overrides. A retraction restricts $h$ to the part of its domain outside $X$.

4.4 Tests

In practice, sentences are written in natural language and these judgments are made heuristically. Sentences are written as mathematical prose, with explicit quantifiers and domains and defined terms.

Definition 4.7 (Test). A test of $\forall x \in D.\ P(x)$ checks $P(a)$ for a sampled $a \in D$ by running the program. A test belongs to the sentence it was derived from, or to several sentences when only together they entail the case it checks. Tests are sound: a program that satisfies $S$ passes every test belonging to sentences of $S$.

Tests are subordinate to sentences, and code to tests. A test changes only when its sentence changes, and code changes only to make tests pass, generalizing as its sentences do rather than special-casing the tested inputs.

5. The software engineering loop

5.1 State and reconciliation

Definition 5.1 (State). The state of a project is a triple $(S, T, p)$ of a specification, a test suite and a program, subject to three invariants:

  1. $S$ is satisfiable;
  2. every test in $T$ belongs to sentences in $S$;
  3. $p$ type-checks and passes every test in $T$.

The initial state is $(\emptyset, \emptyset, p_0)$.

When the specification changes, reconciliation restores the invariants:

  1. remove every test whose sentence was removed, or whose sample now lies outside its sentence’s domain;
  2. add tests for any new sentence;
  3. modify the program until it type-checks and passes every test.

Since the specification is satisfiable and tests are sound, some program passes every test. The loop assumes the developer finds one.

5.2 The loop

Procedure 5.2 (Software engineering loop). New information $\delta_t$ takes $(S_t, T_t, p_t)$ to $(S_{t+1}, T_{t+1}, p_{t+1})$:

  1. If $\delta_t$ is a counterexample that cannot be reproduced, discard it.
  2. Apply the entailment check. If neither conjecture is refuted, discard $\delta_t$.
  3. If correctness is refuted, keep $S_{t+1} = S_t$ and add the instance of $\delta_t$ as a test.
  4. If adequacy is refuted by a sentence or a counterexample, let $g_t$ be the sentence or the counterexample’s generalization, and let $S_{t+1}$ be a revision of $S_t$ by $g_t$. If $\delta_t$ is a counterexample, add its instance as a test of $g_t$.
  5. If $\delta_t$ is a retraction of $h$ on $X$, restrict $h$ to the rest of its domain.
  6. Reconcile the tests and the program with $S_{t+1}$.
  7. If step 4 restricted any sentence, report the conflict to the people involved.
  8. Deploy $p_{t+1}$. Its behavior and new requests supply $\delta_{t+1}$.

Each iteration preserves the invariants. The loop runs as long as new information arrives.

5.3 Example

Example 5.3 (Withdrawal, continued). Let $X$ be the inputs $x = (b, k, m)$ of Example 2.6, let $\mathrm{succeeds}(x)$ mean the new balance is $b - m$, and let $\mathrm{rejected}(x)$ mean it remains $b$. The working specification starts with three sentences: $$\begin{aligned} \varphi_1 &: \forall x \in D_1.\ \mathrm{succeeds}(x), & D_1 &= \{x \in X : 0 < m \le b\}, \\ \varphi_2 &: \forall x \in D_2.\ \mathrm{rejected}(x), & D_2 &= \{x \in X : m > b\}, \\ \varphi_3 &: \forall x \in D_3.\ \mathrm{rejected}(x), & D_3 &= \{x \in X : m \le 0\}. \end{aligned}$$

A new requirement. The bank states that premium accounts may overdraw by up to $100: $$g_1 : \forall x \in G.\ \mathrm{succeeds}(x), \qquad G = \{x \in X : k = \mathrm{premium},\ m > 0,\ b < m \le b + 10000\}.$$ On $G$, $\varphi_2$ requires rejection, so $S$ does not entail $g_1$ and adequacy is refuted. $D_1$ and $D_3$ are disjoint from $G$, so the revision restricts $\varphi_2$ alone, to $D_2 \setminus G$, and adds $g_1$.

A defect. The bank reports that a premium account with $50 withdrew $200: the condition $(5000, \mathrm{premium}, 20000)$ succeeded where rejection was expected. The condition lies in $D_2 \setminus G$, so $\varphi_2$ entails the instance and correctness is refuted. The instance becomes a test of $\varphi_2$, and the program is fixed.

An inadequacy reported as a defect. The bank reports that a standard account with $100 was allowed to withdraw 5 cents, though its machines dispense only whole dollars. The condition $(10000, \mathrm{standard}, 5)$ lies in $D_1$, where $\varphi_1$ requires success, so adequacy is refuted. The bank generalizes: $$g_2 : \forall x \in H.\ \mathrm{rejected}(x), \qquad H = \{x \in X : m \bmod 100 \ne 0\}.$$ The revision restricts $\varphi_1$ to $D_1 \setminus H$ and $g_1$ to $G \setminus H$, and adds $g_2$.

The last two reports have the same form, and the entailment check tells them apart: the first changes the program, the second the specification.

5.4 The loop in the decision process

The loop carries out the approximation of Definition 3.3: $S_t$ is $\hat{S}_t$, steps 1 to 5 are the revision $U$, and reconciliation is the policy, which pays the cost of modification by starting from $p_t$. The test suite is the developer’s executable record of what $S_t$ requires.

If every sentence in $S_t$ and $g_t$ holds of the current objective, then $S_t \cup \{g_t\}$ is satisfiable and the revision restricts nothing. A restriction therefore means that either the objective has moved or an earlier sentence was stated too generally. Like the ideal belief update, the loop handles both with one operation, and step 7 hands the question to the people who can answer it.

6. Discussion

Automation. The model contains three maps: forming the working specification from the first requests, revising it from new information, and producing a program from it. Each can be performed by a person or by an AI agent, and the model does not depend on whether people retain an advantage at any of them. It does suggest that measuring an agent’s ability to produce a program for a stated specification mostly measures capability, and leaves the belief side of the problem largely unmeasured.

Limitations. Empirical work could ask how often reported defects in real projects are inadequacies rather than incorrectness, and whether agents that maintain an explicit working specification and apply the entailment check reach accepted programs in fewer iterations than agents that do not. The model allows the objective to move but says nothing about how it moves. A specification that is too strong is never exposed by a rejection, so the loop corrects it only when the stakeholder retracts something. And the representation of Section 4 handles only new information that can be stated as sentences; feedback that resists such statement, such as general dissatisfaction with an interface, has a place in the decision process but not in the loop.

7. Related ideas

The observations the model starts from are old. Brooks (1987) located the essential difficulty of software in deciding what to build, Swartout and Balzer (1982) argued that specification and implementation cannot be separated in time, Naur (1985) described programming as theory building, and Lehman (1980) observed that software in use must keep changing. In requirements engineering, Zave and Jackson (1997) separate requirements, domain knowledge and specifications, and Boehm (1984) separates validation from verification, which appear here as checks of adequacy and of correctness.

The model borrows its parts. Its decision process is close in structure to cooperative inverse reinforcement learning (Hadfield-Menell et al. 2016), in which an agent is uncertain about a human’s objective and learns it through interaction. Program synthesis (Gulwani et al. 2017) is the capability factor. Its counterexample-guided loops (Solar-Lezama et al. 2006) refute a candidate program against a fixed specification, whereas the loop here must also handle counterexamples that refute the specification. Learning from queries and counterexamples (Angluin 1987) likewise assumes a fixed target. In belief revision (Alchourrón et al. 1985), Katsuno and Mendelzon (1991) distinguish revising beliefs about a static world from updating them when the world changes; the loop handles both with one operation. Test-driven development (Beck 2003) organizes code around tests, where the loop makes tests subordinate to sentences. Benchmarks for code generation (Chen et al. 2021; Jimenez et al. 2024) largely measure capability, and Lahiri et al. (2022) use tests to clarify intent before generating code. Finally, the working specification is a conjecture in the sense of Popper (1963): new information refutes either it or the claim that the program satisfies it.

8. Conclusion

We have modeled software engineering as a partially observable decision process whose hidden state is the specification the stakeholder currently holds, and which moves in response to what is built. In the model, acceptance depends on capability and on belief, and a rejection reflects one of two failures that call for different remedies: an incorrect program or an inadequate specification. Replacing the belief with a single working specification, written as a finite, satisfiable set of sentences, turns the abstract process into something that can be operated: new information is classified by the conjecture it refutes, the specification is revised accordingly, and tests and code are reconciled with it. Programs are the actions taken along the way; the specification is the state that development maintains.
